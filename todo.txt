2. 赛后把比赛存进知识库(RAG/Wiki/知识图谱?)—— ⚠️ 方向对,但别建知识图谱
先纠正一个架构认知:不同数据该进不同的库,别一股脑塞向量库。

数据类型	该放哪	现状
结构化事实(预测/真实比分/概率)	关系库 MySQL(你已经有 predictions 表!)	追问"你当时预测啥"其实是一条 SQL,根本不用 RAG
非结构化叙事(战报/新闻/伤病)	向量 RAG	历史世界杯已入库;赛后战报可追加

知识图谱:能做多跳关系查询(“阿根廷历史上几次逆转埃及”),但构建+维护成本极高,对你现在的规模是过度设计(和你那份 RAG 备忘的结论一致——别 cargo-cult)。你现在的关系查询用 SQL/API 就够。先不做 KG。
真正该做的:① 把问题1的根因修了(给追问以工具/检索,见下方优先级);② 赛后把 resolved 比赛的结构化事实本就在 MySQL,只需让 agent 能查;③ 可选:把赛后战报追加进 RAG 供叙事召回。这三件都比建 KG 便宜、见效快。
3. 多比分概率(加总 100%,默认给概率最大的若干)—— ✅ 好,但注意校准
这是足球预测的标准做法(比分分布,通常用 Poisson/Dixon-Coles 模型从预期进球推)。比单一比分更诚实、更有信息量。
坑:直接让 LLM 吐一堆比分概率,校准会很差(LLM 的数字不可信)。更稳的是:让模型给期望进球/强弱,用 泊松分布算比分概率矩阵。但这是额外建模工作。
评价对齐:多比分要用 RPS(排序概率得分) 或对精确比分的 log-loss 来评,现在的 3 路 Brier 仍作主指标。
建议:做,但排在流式和追问修复之后。先让模型输出 top-N 比分+概率用于展示,评估主指标仍用 1x2 Brier,RPS 作为增补。别指望 LLM 的比分概率很准。
4. 每次预测后更新能力(核心)—— 见下方专门小节,先给结论
诚实说:你现在有"评价",但没有"更新"。 这是最大的缺口,也是最该慎重设计的地方(避免自我强化偏差)。详见下一节。

6. (你的这条是"请我评价")—— 已在做
关于第 4 点:现在的评价方法 & 更新策略(核心,先给全景)
现在的评价方法(已有):

每条预测存 MySQL(p_home/draw/away + 比分)。
赛后 resolver 拉真实比分 → 判胜平负 → 算 Brier(你) 和 Brier(赔率基准) + log-loss。Brier 越低越准。
汇总:平均 Brier 你 vs 赔率、你击败赔率的场次。核心基准 = 能不能打赢市场赔率(实测目前没打赢,≈复述市场)。
现在的更新策略:没有。 预测之间彼此独立,eval 只度量、不回流。这是缺口。

现实的"学习"路径(按 ROI 排序,后面细聊):

校准(calibration) — 最高性价比。用已结算数据学一个校准函数(向市场收缩 / 温度缩放),纠正系统性过度自信。便宜、有效、可量化。
案例检索(case-based / 对自己战绩做 RAG) — 预测时检索相似历史案例("你上次淘汰赛高估了强队,实际爆冷")喂进上下文。和想法 2 天然合流。
提示词/启发式迭代 — 定期分析系统性错误,把教训写进 system prompt。半自动。
微调 — 数据量太小、成本高、收益不确定。不做。
一个必须诚实的架构判断:agent 的准确度上限主要由输入数据决定(赔率、状态、伤病),不是靠"自我学习"就能突破;打赢赔率本身极难。所以"更新能力"最该追求的不是"更聪明",而是别过度自信(校准)+ 会引用自己的历史教训(案例检索)。把期望值放对,才不会在这上面投入过度。
